

Below is a plan built around my jailbroken Oasis 3 target resolution: **1264 × 1680 @ 300 dpi**.

---

## Goal

Turn a web dashboard into a deterministic **e-ink frame generator**.

Prove it in a desktop “Kindle viewer” test bed first. Then integrate with the Kindle via KOReader.

---

## Part 1: Web app to e-ink picture generator, with a Kindle viewer test bed

### 1.1 Define the contract

You will standardize one output.

* Output file: `dashboard.png`
* Size: `1264x1680`
* Color mode: grayscale
* Update cadence: configurable, start at 300s
* Must include: “last updated” timestamp rendered into the image

Acceptance criteria:

* Same inputs produce the same pixels.
* Image is readable at 60 cm distance.
* No tiny text, no thin lines.

---

### 1.2 Build the web dashboard for rendering

Keep it boring and printable.

Rules:

* White background only.
* Black text only.
* One column layout.
* Large typography.
* No animations.
* Avoid shadows and gradients.

Implementation notes:

* Use system fonts or bundle one font file.
* Make a dedicated “render route” like `/render`.
* Ensure it looks correct at exactly 1264x1680.

Deliverable:

* A web page that looks like the final dashboard in a browser window sized to 1264x1680.

---

### 1.3 Add an e-ink rendering pipeline

Use an HTML to image renderer.

Recommended approach:

* Playwright screenshot of `/render` at a fixed viewport.

Pipeline steps:

1. Start local server.
2. Open `/render` with Playwright.
3. Wait for a “render ready” marker.
4. Screenshot to `dashboard.raw.png`.
5. Post-process to e-ink friendly `dashboard.png`.

Post-processing checklist:

* Convert to grayscale.
* Increase contrast slightly if needed.
* Optional dithering toggle for photos, off for text dashboards.

Deliverables:

* `render_dashboard.py` or `render_dashboard.ts`
* Produces `out/dashboard.png` on demand

Acceptance criteria:

* Running the renderer 10 times produces identical output for the same data.
* Image generation time stays under 2 seconds locally.

---

### 1.4 Build the “Kindle viewer” desktop test bed

You want a quick feedback loop without touching the Kindle.

Viewer requirements:

* Displays `dashboard.png` at 1264x1680.
* Scales it to your screen while preserving aspect ratio.
* Simulates e-ink limitations.

Simulation features:

* Optional grayscale quantization (4 to 16 levels).
* Optional ghosting simulator (blend current frame with previous).
* Optional “full refresh” button that clears ghosting.

Implementation options:

* Simple local web page that reloads the image.
* A tiny Python app with a window that refreshes.
* Even a script that opens the PNG and reloads is fine, as long as it is fast.

Test protocol:

1. Run a loop that regenerates `dashboard.png` every 60s.
2. Viewer auto reloads every 60s.
3. Let it run for 2 hours.
4. Check for layout drift, flicker, partial render, and slowdowns.

Deliverables:

* `viewer/` with one command to run
* A “soak test” script that runs render + reload for 2 hours

Acceptance criteria:

* Zero crashes over a 2 hour soak test.
* No cumulative layout shifts.
* No missing glyphs or font fallback surprises.
* Readability stays high across updates.

---

### 1.5 Finalize a baseline dashboard template

Lock the first version before Kindle work.

Pick a stable layout:

* Header: time, date
* Block 1: 2 to 4 key metrics
* Block 2: short status list
* Footer: last updated, data source health

Deliverable:

* A template dashboard that you will not change during Part 2 integration work.

## Part 2: Integrate with the Kindle Oasis via KOReader

### 2.1 Decide the transfer mechanism

Start with the easiest.

Phase 2A, USB sync:

* Your computer writes to the mounted Kindle volume.
* Best for early development.

Phase 2B, Wi-Fi sync:

* Enable SSH on the Kindle.
* Use `scp` or `rsync` to push `dashboard.png`.
* Best for a permanent desk setup.

Deliverable:

* One command `sync_dashboard` that overwrites `/mnt/us/dashboard/dashboard.png`.

Acceptance criteria:

* Sync is idempotent.
* A partial file never appears on device.
* You always copy to a temp file then rename.

---

### 2.2 Create a KOReader “Dashboard mode” plugin

This is the kiosk layer.

Plugin responsibilities:

* Open `/mnt/us/dashboard/dashboard.png`.
* Show full-screen.
* Refresh on a timer.
* Provide manual refresh.
* Do a full e-ink refresh every N cycles to reduce ghosting.
* Optionally prevent sleep while active.

UI minimalism:

* One menu entry: “Start Dashboard”.
* One entry: “Stop Dashboard”.

Deliverable:

* `/mnt/us/koreader/plugins/dashboard.koplugin/` folder with Lua code.

Acceptance criteria:

* One tap starts it from KOReader.
* It runs for 8 hours without manual intervention.
* Refresh cadence is consistent.

---

### 2.3 Ghosting and refresh tuning

E-ink behavior matters more than code elegance.

Knobs to expose:

* Refresh interval in seconds.
* Full refresh every N updates.
* Optional “invert” mode if contrast looks better.

Test protocol on device:

* Run 4 hours at 300s refresh.
* Then run 4 hours at 120s refresh.
* Compare ghosting, battery, and readability.

Acceptance criteria:

* Ghosting remains acceptable.
* No UI burn-in patterns from static chrome.
* Battery drain is reasonable for your desk use.

---

### 2.4 Operational hardening

Make it something you can forget.

Hardening steps:

* Add a watchdog on your computer that restarts the renderer if it fails.
* Add a “data stale” indicator on the image if inputs stop updating.
* Log each render with a timestamp and a success flag.
* Keep the last 10 images for debugging.

Acceptance criteria:

* If rendering fails, the dashboard clearly indicates it.
* Recovery is automatic without you touching the Kindle.

---

## Suggested repo structure

Keep it simple.

* `dashboard-web/` web app with `/render`
* `renderer/` Playwright render script + postprocess
* `viewer/` desktop kindle-sim viewer
* `sync/` USB and optional Wi-Fi sync scripts
* `koreader-plugin/` final plugin folder
